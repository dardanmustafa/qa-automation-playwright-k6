# BUG-010 · OSM API: caching (304 Not Modified) never works for compressed answers

| Field | Value |
|---|---|
| Type | Defect |
| Severity | Medium (performance: wasted bandwidth and server work) |
| Priority | Medium |
| Area | OpenStreetMap API 0.6 › HTTP caching (ETag / conditional requests) |
| Environment | `https://master.apis.dev.openstreetmap.org/api/0.6` (Apache in front of the Rails app) |
| Reproducible | Always |
| Found by | Automated test `API-NOTE-11` failed under Playwright but passed with curl; now automated as `API-NOTE-12` in [`api/tests/notes.spec.ts`](../api/tests/notes.spec.ts) |

## Summary

The API supports conditional requests: send back the `ETag` you received, and the server answers **304 Not Modified** with an empty body if nothing changed. This works only when the answer was **not** compressed.

Almost every real client (all browsers, most HTTP libraries) asks for gzip. The compressed answer carries a modified ETag ending in `-gzip`, and the server never recognises that ETag again. So it always sends the full answer.

## Steps to reproduce

```bash
URL=https://master.apis.dev.openstreetmap.org/api/0.6/capabilities.json

# Compressed (like a browser)
curl -s -D - -o /dev/null -H "Accept-Encoding: gzip" $URL | grep -i etag
#  etag: W/"8204cb2747eaf4689cd05fa8ea0c1f2f-gzip"
curl -s -o /dev/null -w "%{http_code}\n" -H "Accept-Encoding: gzip" \
     -H 'If-None-Match: W/"8204cb2747eaf4689cd05fa8ea0c1f2f-gzip"' $URL
#  200   <- expected 304

# Uncompressed
curl -s -o /dev/null -w "%{http_code}\n" -H 'If-None-Match: W/"8204cb2747eaf4689cd05fa8ea0c1f2f"' $URL
#  304   <- works
```

## Expected result

`304 Not Modified` whenever the ETag the client sends back is the one it received, compressed or not.

## Actual result

| ETag sent back | With `Accept-Encoding: gzip` | Without |
|---|---|---|
| `W/"…-gzip"` (the one a gzip client receives) | **200** (full body) | **200** |
| `W/"…"` (uncompressed ETag) | 304 | 304 |

## Impact

Caching is effectively switched off for real-world clients. Every repeated request downloads and computes the full answer again, which costs bandwidth for users and load for the OSM servers.

## Notes

This is the known behaviour of Apache `mod_deflate`: by default it appends `-gzip` to the ETag (`DeflateAlterETag AddSuffix`), and the application behind it compares against its original ETag. Possible fixes:

- `DeflateAlterETag NoChange` (Apache ≥ 2.4.58)
- strip the suffix from `If-None-Match` before it reaches the app
- let the app do the compression itself
