# BUG-013 · OSM API: map data requests are refused (406) when `Accept-Encoding` has no spaces after the commas

| Field | Value |
|---|---|
| Severity | Medium (clients that send a valid header cannot read map data at all) |
| Priority | Medium |
| Area | OpenStreetMap API 0.6 › map data reads (`/node/{id}`, `/map`, `/nodes`, …) › content encoding |
| Environment | `https://master.apis.dev.openstreetmap.org/api/0.6` (official development server) |
| Reproducible | Always |
| Found by | The signed-in test `API-MAP-07` failed with 406 the first time it ran with a token; now automated as `API-MAP-13` in [`api/tests/map-data.spec.ts`](../api/tests/map-data.spec.ts) |

## Summary

Requests for map data answer **406 Not Acceptable** when the `Accept-Encoding` list is written without spaces, e.g. `gzip,deflate,br`. The same list with spaces, `gzip, deflate, br`, works. HTTP allows both forms ([RFC 9110, section 5.6.1](https://www.rfc-editor.org/rfc/rfc9110#section-5.6.1): the space after a comma is optional).

`gzip,deflate,br` is exactly what Playwright sends by default, so any test or tool built on it gets 406 for every node, way or map request. The error message is wrong too: it says only identity and gzip are supported, but the server answers with `br` and `deflate` when the header has spaces.

Notes and `capabilities` are not affected; only the map data endpoints are.

## Steps to reproduce

```bash
URL="https://master.apis.dev.openstreetmap.org/api/0.6/map.json?bbox=0.0001,0.0001,0.0002,0.0002"

curl -s -o /dev/null -w "%{http_code}\n" -H "Accept-Encoding: gzip,deflate,br"   "$URL"
#  406   <- expected 200
curl -s -o /dev/null -w "%{http_code}\n" -H "Accept-Encoding: gzip, deflate, br" "$URL"
#  200

curl -s -H "Accept-Encoding: gzip,deflate" "$URL"
#  No acceptable content encoding found. Only identity and gzip are supported.
```

## Expected result

`200 OK`, compressed with one of the listed encodings (or not compressed), whether or not there are spaces after the commas.

## Actual result

Reading an existing node (`GET /node/{id}.json`) with different headers:

| `Accept-Encoding` | Status | Encoding of the answer |
|---|---|---|
| `gzip,deflate,br` (Playwright's default) | **406** | – |
| `gzip, deflate, br` | 200 | br |
| `gzip, deflate` | 200 | deflate |
| `gzip` | 200 | gzip |
| `br` | 200 | br |
| `identity` | 200 | none |

More variants on the map data call from the steps above (`GET /map.json`, 26 Oct 2026). A comma that is not followed by a space always gets 406:

| `Accept-Encoding` | Status | Encoding of the answer |
|---|---|---|
| `gzip,deflate` | **406** | – |
| `gzip,br` | **406** | – |
| `gzip ,deflate` (space before the comma) | **406** | – |
| `gzip;q=1.0,deflate;q=0.5` | **406** | – |
| `gzip;q=1.0, deflate;q=0.5` | 200 | gzip |
| `gzip,  deflate` (two spaces) | 200 | gzip: `deflate` is ignored, unlike with one space |
| `foo` (an encoding the server doesn't know) | **406** | – (HTTP says the server should answer uncompressed instead, [RFC 9110, section 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3)) |

## Impact

- Clients and test tools that send a compact header cannot read map data, although their request is valid.
- The message "Only identity and gzip are supported" sends developers in the wrong direction.

## Notes

- **Workaround used in this project:** [`playwright.api.config.ts`](../playwright.api.config.ts) sends `Accept-Encoding: gzip, deflate, br` (with spaces) for all API tests.
- **Cause, confirmed in the source code:** map data reads are answered by CGImap, the C++ program OSM runs for its most used map data calls; the error text in the steps above is CGImap's. Its `choose_encoding` function splits the header on the exact text `", "` ([`src/http.cpp`, line 159](https://github.com/zerebubuth/openstreetmap-cgimap/blob/0e1840f2a7d96c53bc1016bf15bd4f71888c8095/src/http.cpp#L159)), so `gzip,deflate,br` is read as one unknown encoding. When it recognises none of the listed encodings, it refuses the request instead of answering uncompressed ([lines 163](https://github.com/zerebubuth/openstreetmap-cgimap/blob/0e1840f2a7d96c53bc1016bf15bd4f71888c8095/src/http.cpp#L163) and [230–234](https://github.com/zerebubuth/openstreetmap-cgimap/blob/0e1840f2a7d96c53bc1016bf15bd4f71888c8095/src/http.cpp#L230-L234)).
