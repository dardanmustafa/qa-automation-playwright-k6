# IMP-001 · OSM API: offer JSON error answers on `.json` endpoints

| Field | Value |
|---|---|
| Type | Improvement suggestion (not a defect: the API works as designed) |
| Priority | Low |
| Area | OpenStreetMap API 0.6 › error responses |
| Environment | `https://master.apis.dev.openstreetmap.org/api/0.6` (official development server) |
| Found by | API exploration. `API-NOTE-09` in [`api/tests/notes.spec.ts`](../api/tests/notes.spec.ts) checks the current behaviour |
| History | First filed as BUG-008, then reclassified after checking how OSM defines its errors (see below) |

## Summary

When a client asks for JSON (an endpoint ending in `.json`), successful answers are JSON, but error answers are not. A 400 comes back as plain text, and a 404 for a malformed URL as a full HTML web page. A client that always parses the body as JSON fails on errors instead of showing the message.

## Why this is not a bug

OSM reports errors this way on purpose. Its [`report_error`](https://github.com/openstreetmap/openstreetmap-website/blob/master/app/controllers/application_controller.rb) method sends the message as plain text and also in an `Error` response header. A client that wants a structured error can send `X-Error-Format: xml` and gets an `<osmError>` XML document (with HTTP status 200 and the real status inside the XML). There is no JSON error format, and the [API documentation](https://wiki.openstreetmap.org/wiki/API_v0.6) does not promise one.

## Current behaviour

```bash
# 1. Invalid location -> 400
curl -i -X POST "https://master.apis.dev.openstreetmap.org/api/0.6/notes.json?lat=91&lon=0&text=x"

# 2. Invalid id -> 404
curl -i "https://master.apis.dev.openstreetmap.org/api/0.6/notes/abc.json"
```

| Request | Status | Content-Type | `Error` header | Body |
|---|---|---|---|---|
| `POST /notes.json?lat=91…` | 400 | `text/plain; charset=utf-8` | `The note is outside this world` | `The note is outside this world` |
| `GET /notes/abc.json` | 404 | `text/html; charset=utf-8` | – | a complete "File not found" HTML page (~6 KB) |

## Suggestion

For endpoints ending in `.json`, answer errors with `Content-Type: application/json` and a JSON body, for example:

```json
{ "error": "The note is outside this world" }
```

Keep the `Error` header so existing clients keep working.

## Benefit

Clients of the JSON endpoints could handle errors with the same code as successful answers, instead of special-casing plain text and HTML.
